# Universal POS QR integration

This addon creates one Stage A request per posted customer invoice and supports INR partial payments. The wizard button saves a request and opens it; **Submit / Retry to POS** is a second action, so the request reference is committed before contacting the POS. It does not register an Odoo payment. A signed capture callback posts and reconciles a payment through Odoo's payment-register wizard, with any unpaid balance left open.

Only accounting users can view and operate requests, restricted to their allowed companies. Only system administrators can view or configure API secrets. Each request snapshots the instance, URL, key and bank journal so retries and callbacks retain their original identity across configuration changes. API keys are stored in the Odoo database, including snapshots: protect database backups and administrator access. Do not revoke old POS clients while their requests or callbacks remain outstanding.

The prepared, uncertain, creating, ready and ambiguous states reserve their amount against the invoice. Requests are deliberately never automatically released, even when an operator sees an apparent expiry: a capture or a delayed callback can still exist. Stage A has no resolution endpoint for ambiguous requests. Investigate in POS/Razorpay and use a reviewed operational recovery procedure; do not manually remove reservations or create replacement requests until all payment and callback outcomes are known. Ordinary Odoo payments can change the invoice independently; submission and callback reject insufficient balances, requiring manual accounting investigation. Do not use this module as a replacement for operational monitoring.

## Configuration and installation (manual; test first)

1. Take a verified backup of Odoo database and filestore. Install the addon first on an isolated Odoo 17 test database with fake POS credentials and mocked transports; run the addon tests. Do not reuse a production database for tests.
2. In the applicable company's administrator-only POS QR settings, configure the HTTPS POS API base URL, Stage A instance, client API key and a bank journal belonging to that company. The journal must have an inbound manual payment method and an appropriate outstanding-receipts account. Each request snapshots these settings.
3. Configure the POS Stage A client with its exact callback URL `https://<odoo-host>/universal_pos_qr/callback`, matching the backend's `ODOO_CALLBACK_URLS` allowlist. Route this path to exactly the intended Odoo database, using the Odoo reverse proxy and dbfilter. Enable the Stage A callback worker and monitor deliveries. Ensure HTTPS and protect both credentials and the Odoo database. Do not enable cutover until isolated end-to-end checks, access-control review, accounting and concurrency testing pass.
4. After explicit deployment approval, install `universal_pos_qr` using the normal Odoo module installation workflow. This adds Odoo database tables and fields. Follow the normal approved service/module upgrade procedure; this change does not itself restart a service or update a database.
5. In a non-production test environment, create and submit partial and full requests using mock Razorpay/POS transports. Exercise timeout and identical-reference retry, duplicate callbacks, signature failures, wrong invoice/customer/amount/currency, insufficient residual, concurrent requests and accounting reconciliation. Confirm the original Register Payment buttons and other methods still work.

For automated Odoo tests, run Odoo against a newly created disposable test database with `--addons-path` including core addons and `customaddons`, `-i universal_pos_qr --test-enable --test-tags /universal_pos_qr --stop-after-init`. Never point that command at a live database. `tests/test_signature_standalone.py` and `tests/test_contract_standalone.py` use Python's standard library and do not contact the POS.

## Rollback

Disable the UI or stop new requests using the approved release procedure; preserve the addon, database tables, keys, POS mappings and callback route while outstanding requests or callback deliveries exist. Reconcile unresolved and captured payments first and keep the callback worker operational. Restoring older Odoo application code without this callback can interrupt delivery. Uninstalling the module or deleting its tables loses tracking and deduplication and is unsafe with outstanding events; use a tested backup and a reviewed accounting recovery plan before any removal. Do not downgrade POS migration 0003 while mappings or payments need retention.
